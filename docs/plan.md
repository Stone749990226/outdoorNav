## 2. Service、Skill 与本次模块划分

Robonix 的 **Service 是提供算法或持续功能的软件组件**，例如建图、导航、语音。它注册到 Atlas，接受生命周期管理，并通过能力接口供其他组件调用；它不等同于 ROS2 的 service 请求—响应接口，一个 Robonix Service 可以同时使用 ROS2、gRPC 和 MCP。

**Skill 是封装可复用任务行为的组件**，例如“探索某区域”“执行取送流程”。当前 Executor 会在调用前激活 Skill。Service 和 Skill 都能被模型调用；并非只有 Skill 才能让 Pilot 使用，也不是每个 Service 上面都必须增加 Skill。

源码依据：[Service／Skill 实现](/home/stone/learn/outdoorNav/robonix/pylib/robonix-api/robonix_api/capability.py:978)、[Executor 激活逻辑](/home/stone/learn/outdoorNav/robonix/system/executor/src/dispatch/mod.rs:1)。

**首版不新增 Skill。** “到指定室外地点”是确定性的导航功能，由室外导航 Service 提供完整能力。以后“到达—等待交接—确认装载—返回”的流程稳定后，再封装为 Skill，复用导航服务。

模块落点：

| 模块 | 类型 | 职责 |
|---|---|---|
| GNSS 接入 | Primitive | 单一串口采集、NTRIP、标准定位消息与质量状态 |
| 地理定位 | Service | GNSS 与厂商里程计对齐，提供统一地理位姿 |
| 全局地图／室外导航 | Service | 人工地点、道路图、选路、整次导航任务与反馈 |
| 现有 nav2 | Service，扩展 | 执行参考路线、感知绕障、速度控制与停车 |
| 网页 | 应用 | 人工标注、路线预览、定位与任务状态显示 |

运行链路：

```text
控制台 → Liaison → Pilot → Executor
                          ↓
              室外导航 Service
              人工地点解析＋路网选路
                          ↓
                 现有 nav2 Service
              连续路线规划＋局部避障
                          ↓
              速度平滑／guard → 底盘

GNSS＋厂商里程计 → 地理定位 → 规划与执行
雷达点云 → 障碍代价地图 → 规划与执行
```

## 3. 具体实施方案

### 人工语义地点与全局路网

- 全局服务管理地理坐标基准、道路图和人工地点；语义标注与路网使用同一份坐标变换和版本。
- 复用本项目已有的道路图、Dijkstra 和有序路线引导，不迁移 Gazebo 场景几何及仿真定位节点。
- 首批示例使用现有路网节点，不随意编造坐标：

| 示例名称 | 绑定节点 | 用途 |
|---|---|---|
| 出发点 | S：环线起点 | 起点示例 |
| 公共路口 | J：公共路口 | 自然语言导航目标示例 |
| 支路取餐点 | P：支路端点 | 取餐目标示例 |

- 示例标注注明“演示、待现场确认”；真实取餐点的位置与停车朝向经现场确认后启用。路口应选择适合停车的位置，不能默认停在路口中心。
- 网页提供地点新增、改名、拖动、删除及朝向设置。地点持久化到版本化地图数据，控制台和网页共用。
- 首版不启用自动检测模型。暂不要求启用 Scene；未来通过适配接口将 Scene 的人工标注或自动检测结果关联到稳定地点 ID，不重复维护两份可编辑地理坐标。

### GNSS 与地理定位

- 保留现有 `start.sh` 的使用方式与 NTRIP 连接后补发 GGA 的修正，将其采集实现整理为可复用模块。
- GNSS Primitive 管理同一采集实现、虚拟环境和现有文件锁；通过解析回调发布数据，不解析终端日志，也不增加第二个串口读取者。
- 发布 `NavSatFix`，并单独暴露固定解状态、hAcc、差分时效、卫星数和数据新鲜度。正确处理 NAV-PVT 的毫米单位、椭球高与海拔差异；凭据继续保存在机器人现有私有配置中。
- 首版以已验证的 `/ODOM` 为局部运动输入；不依赖尚未收到数据的 LIO 话题。输入需检查时间戳、有限数值、四元数、异常跳变和重置；零协方差不能解释为零误差。
- 室外使用与道路数据一致的 ENU 基准。首版通过现场测量完成初始位置、航向及天线安装偏移标定，不把静止 GNSS 的 `headMot` 当作绝对航向。
- 地理定位服务使用 GNSS 校正位置、使用已对齐的里程计提供连续运动；只由该服务发布室外 `map→odom`。室外配置不同时运行 RTAB-Map 的同名 TF 修正。
- 默认进入导航需连续 5 秒固定解、hAcc≤0.20 米、差分年龄≤5 秒，且完成坐标对齐。GNSS 或里程计超过 1 秒未更新、解质量不再满足条件，停止当前导航；首版不自动降级为纯里程计继续行驶。

### 路线执行与避障

- 扩展现有 nav2 Service，增加“跟随有序参考路线”的入口，保留单点导航兼容性。
- 首版直接复用本项目已实现的有序短段、滚动窗口和逐段 NavFn 路径拼接逻辑，将执行调度放进 nav2 Service；继续使用山猫现有 DWB、速度平滑和 guard。
- 单点导航与路线导航共享运动所有权。替换任务必须取消旧执行并确认停车，避免 BT 与新增执行逻辑同时调用控制器。
- 新建独立室外参数配置：使用雷达障碍层、膨胀层及允许未知区域的规划，不依赖尚不存在的完整校园栅格地图；传感器未观测区域不解释为已确认安全。
- 保留道路弯折、按顺序推进；中间引导点不作为停车任务。局部绕障可以偏离参考线，但不得通过跳过后续道路抄近路。
- guard 同时支持两种任务入口，路线任务使用真实最终目标，不能误把滚动窗口末端当作终点。所有速度继续经过同一受控输出链。
- 首版支持局部绕障和人工封路选路；持续堵路时停车并报告失败，不自动永久封闭道路。
- 实机初始线速度上限设为 0.15 米／秒，到达容差为 0.50 米；确认停车后再判定成功。

### Robonix 接口与部署

- 全局服务提供地点查询、路线预览，以及按地点 ID 启动导航、查询状态、取消任务。
- 导航返回 `run_id`，按 Robonix 既有异步约定注册配套状态与取消接口；网页另取结构化遥测，显示当前位置、参考路线、执行路径和剩余路程。
- nav2 新增路线执行能力，输入有序 `Path` 与地图／路线版本，同样具有状态和取消接口；上层整次任务关联其执行 `run_id`。
- 面向 Pilot 的室外导航入口使用 MCP；组件之间通过 Atlas 发现并使用确定性接口。控制台任务不绕过全局服务直接给 nav2 发最终终点。
- 新包加入山猫主工程，通过正式包清单构建和启动；导航修改落在可维护的源码仓库，不只修改 `rbnx-boot/cache`。
- 重启后不自动恢复运动；保留任务终态与失败原因。首版只提供文本控制台入口。

## 4. 实施顺序与核心验收

1. **数据接入**：将现有 NTRIP 采集纳入 Primitive；验证实时 GNSS 质量、串口唯一占用，以及厂商里程计的更新、延迟和重置行为。
2. **坐标闭环**：完成天线外参、初始航向和 ENU 对齐；网页同时显示机器人、道路及独立实测检查点，确认坐标一致。
3. **全局服务**：导入路网和三个示例地点，完成能力注册、地点查询和封路预览；此阶段不需要机器人运动。
4. **路线闭环**：接入 nav2 连续执行、反馈、取消和替换，先验收短直线，再验收弯道与绕障。
5. **控制台任务**：验证“去公共路口”能查询地点、规划并到达停车；模型不生成底盘速度或逐点控制指令。

只增加必要的核心测试：

- GNSS 日志回放：普通差分与固定解区分、单位换算、失锁和陈旧数据。
- 坐标与路由：标定变换、道路顺序、人工封路，以及示例地点的版本绑定。
- 任务链路：提交、状态、取消、替换，检查取消传递到底层执行。
- 路线执行：弯道保持、中间点不停、障碍绕行、堵路停车与两类导航入口互斥。

现场验收必须包含：已测量目标点的独立到达误差、取消与断流后的真实停车、GNSS 失锁、里程计重置。算法报告成功不能代替停车证据；当前历史 NTRIP 日志也不能代替现场固定解验收。
