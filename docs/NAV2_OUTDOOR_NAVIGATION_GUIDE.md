## 1. 汇报目标与先说结论

这份汇报要回答三个问题：

1. Nav2 在机器人导航系统中负责什么？
2. 室外 RTK 数据怎样转换成 Nav2 能使用的地图和坐标？
3. 当前项目已经接入到哪一步，距离真实机器狗导航还差什么？

先给出结论：**RTK 经纬度不能直接作为 Nav2 的地图坐标。** 需要先选定一个稳定的地理原点，把经纬度转换成局部米制坐标，再用这个坐标建立地图、路径和机器人定位之间的一致关系。

本项目目前已经打通了下面这条链路：

```text
UBX 实测日志
    ↓
局部东-北米制坐标
    ↓
实测道路中心线路网
    ↓
网页 A* 路径规划
    ↓
nav_msgs/Path
    ↓
Nav2 FollowPath
    ↓
仿真机器人 /cmd_vel
```

这条链路证明了路径可以被 Nav2 控制器接收并跟踪，但还不能证明真实道路边界、定位、避障和机器狗底层控制已经完成。因此仓库中的路线仍标记为 `executable_on_robot: false`。

## 2. 先建立一个整体认识：Nav2 是什么

Nav2 是 ROS2 中的一套导航框架。它把“机器人从当前位置走到目标位置”拆成多个相互配合的模块。

可以把一次导航理解成四个问题：

| 问题 | 典型模块 | 作用 |
| --- | --- | --- |
| 哪里能走？ | Map Server、Costmap | 提供静态地图和实时障碍信息 |
| 机器人在哪里？ | 定位系统、TF | 提供机器人相对地图的位置和姿态 |
| 应该怎么走？ | Planner Server | 计算一条可行路径 |
| 怎样沿路走？ | Controller Server | 将路径转换成速度指令 |

常见的完整 Nav2 系统还会包含行为树导航器和生命周期管理器：

- `map_server`：读取地图文件并发布 `/map`。
- `planner_server`：根据起点和终点生成全局路径。
- `controller_server`：跟踪路径，发布 `/cmd_vel`。
- `global_costmap`：描述较大范围内的地图和障碍。
- `local_costmap`：描述机器人附近的实时障碍。
- `bt_navigator`：组织规划、控制、重规划和恢复行为。
- `lifecycle_manager`：按顺序启动和管理 Nav2 节点。

需要区分四个容易混淆的概念：

- **地图**：哪里可以走、哪里是障碍。
- **定位**：机器人当前位于地图中的哪里。
- **路径**：这一次准备经过哪些点。
- **控制**：机器人如何产生速度，沿着路径运动。

地图正确但定位错误，机器人仍然会走偏；路径正确但没有速度控制，机器人也不会运动；控制器正常但地图把建筑标成自由空间，机器人可能向不可通行区域行驶。

## 3. Nav2 中最重要的坐标系

Nav2 通常使用下面的 TF 坐标树：

```text
map
 └── odom
      └── base_link
           └── 传感器坐标系
```

### 3.1 `map`

`map` 是相对固定的世界坐标系。静态地图、规划路径和机器人在园区中的全局位置通常都在这个坐标系中表达。

本项目将 RTK 数据转换为：

```text
X：向东，单位米
Y：向北，单位米
frame_id：map
```

地图原点来自采集数据中的稳定停留段，并保存在 `origin.json` 和 `calibration.json` 中。

### 3.2 `odom`

`odom` 是连续运动坐标系，通常由轮速里程计、视觉里程计或其他短期运动估计提供。它在短时间内比较平滑，但长期可能漂移。

### 3.3 `base_link`

`base_link` 表示机器人本体。激光雷达、相机、GNSS 天线等传感器，都需要通过 TF 描述它们相对于机器人本体的位置和姿态。

### 3.4 为什么不能直接把经纬度传给 Nav2

经纬度是角度单位，Nav2 的路径和代价地图需要连续的米制平面坐标。直接使用经纬度会带来几个问题：

- 纬度和经度不是米。
- 经度对应的实际距离随纬度变化。
- 角度坐标不适合作为局部路径规划的直角坐标。
- 地图、路径、里程计和传感器数据可能使用不同坐标体系。

因此，正确的做法是先选择一个局部原点，将 RTK 位置转换成局部东-北坐标，再把该坐标作为 `map` 中的 `x/y`。

## 4. 本项目如何从 RTK 日志生成米制路网

当前仓库使用 `1.ubx` 和 `2.ubx` 两份日志重建北区道路。处理脚本位于 [tools/build_survey_map.py](/home/stone/learn/outdoorNav/tools/build_survey_map.py)。

处理过程如下：

1. 解析 NMEA 和 UBX 报文，提取时间、经纬度、定位质量和精度估计。
2. 检查时间顺序、重复点和异常跳点。
3. 根据环线末端稳定停留段确定共同原点。
4. 将所有轨迹转换为统一的局部东-北米制坐标。
5. 对轨迹进行停留压缩、异常过滤、短窗口平滑、重采样和简化。
6. 保留弯道和有效转角，不对缺测区间自动补线。
7. 根据确认的公共路口拼接环线和支路。
8. 输出网页路网、轨迹报告以及 ROS2 仿真地图。

生成器的核心输出包括：

- `road_network.json`：米制中心线路网。
- `raw_tracks.json`：原始轨迹。
- `filtered_tracks.json`：过滤后的轨迹。
- `report.json`：处理参数、日志质量和拼接信息。
- `map.svg`：便于检查的矢量图。
- `campus_sim.pgm` 和 `campus_sim.yaml`：当前仿真用占据栅格。

生成命令为：

```bash
conda run -n torch python tools/build_survey_map.py
```

当前输出的质量状态是 `survey_dgps_unverified`。这表示数据可以用于当前演示和仿真，但绝对位置精度尚未通过独立控制点验证。

## 5. 路网地图和 Nav2 占据栅格不是同一种地图

这是本项目最需要向听众解释清楚的地方。

### 5.1 中心线路网

中心线路网是矢量数据，表达道路中心线、节点和道路连接关系。当前网页使用它完成：

- 地图上的 A/B 选点。
- 中心线上的投影。
- 路网 A* 搜索。
- 封路后的可达性判断。
- 完整米制路径和关键途经点导出。

它回答的是：“机器人应该沿着哪条实测中心线走？”

它没有完整表达：

- 道路两侧边界。
- 建筑、台阶和沟渠。
- 临时障碍物。
- 机器人尺寸和安全距离。
- 未测区域是否可通行。

### 5.2 Nav2 占据栅格地图

Nav2 的静态地图通常由图像和 YAML 文件组成：

```text
campus_sim.pgm
campus_sim.yaml
```

YAML 至少需要说明：

- 图像文件。
- 每个像素对应多少米，即 `resolution`。
- 地图原点，即 `origin`。
- 像素值如何解释为空闲、占用或未知。

它回答的是：“在这个二维栅格中，机器人哪些位置可以占据？”

当前仓库中的 [campus_sim.yaml](/home/stone/learn/outdoorNav/ros2_bridge/maps/campus_sim.yaml) 使用 `0.2` 米分辨率；对应的 PGM 是在路网外扩约 10 米后生成的均匀自由空间。这个文件的用途是验证 Map Server 和控制器接口，**不能当作已经测量完成的真实道路障碍地图**。

因此，网页中心线可以先用于路径表达，但实机导航还需要根据道路边界、障碍物和机器人尺寸制作真实占据栅格或其他可供 costmap 使用的地图。

## 6. 当前项目的 Nav2 接入链路

当前项目不是让 Nav2 重新规划中心线路网，而是由网页先完成路网规划，再将完整路径交给 Nav2 的 `FollowPath` 控制器跟踪。

```mermaid
flowchart LR
    A[RTK UBX 日志] --> B[局部东-北米制坐标]
    B --> C[中心线路网]
    C --> D[网页 A/B A*]
    D --> E[完整 map 坐标路径]
    E --> F[HTTP /api/routes]
    F --> G[ROS2 nav_msgs/Path]
    G --> H[Nav2 FollowPath Action]
    H --> I[Regulated Pure Pursuit]
    I --> J[/cmd_vel]
    J --> K[仿真机器人]
    K --> L[/odom 与 TF]
    L --> H
```

### 6.1 网页生成路径

网页在中心线路网中执行 A* 搜索，然后将路径点转换为米制 `map` 坐标。A/B 路径导出逻辑位于 [outdoor-patrol-demo/src/abNavigation.ts](/home/stone/learn/outdoorNav/outdoor-patrol-demo/src/abNavigation.ts)。

导出的路径包含：

- `frame_id: map`。
- 地图版本和配准版本。
- 完整路径点。
- 重要途经点及其朝向。
- 路径长度。
- 推算的 WGS84 经纬度。
- `executable_on_robot: false`。

重要途经点用于展示、检查和任务表达；发送给控制器的是完整路径，而不是稀疏的几个点。

### 6.2 桥接节点发送 `FollowPath`

桥接节点位于 [ros2_bridge/outdoor_nav_bridge/bridge.py](/home/stone/learn/outdoorNav/ros2_bridge/outdoor_nav_bridge/bridge.py)。它会：

1. 检查路径是否使用 `map` 坐标系。
2. 检查地图版本、配准版本和原点是否匹配。
3. 检查路径点是否为有限数值。
4. 按约 `0.25` 米间隔将路径加密。
5. 根据相邻点计算每个路径点的朝向。
6. 发布 `/outdoor_nav/planned_path`。
7. 发布 `/outdoor_nav/waypoints`。
8. 通过 `FollowPath` Action 将路径发送给 Nav2。
9. 读取反馈中的剩余距离，并处理完成、取消和失败状态。

桥接的关键调用是：

```python
goal = FollowPath.Goal()
goal.path = path
goal.controller_id = "FollowPath"
goal.goal_checker_id = "goal_checker"
```

这说明当前系统已经接入了 Nav2 的控制器 Action，而不是只在网页中做轨迹动画。

### 6.3 Nav2 启动内容

启动文件位于 [ros2_bridge/launch/sim.launch.py](/home/stone/learn/outdoorNav/ros2_bridge/launch/sim.launch.py)，当前启动：

- `nav2_map_server/map_server`。
- `nav2_controller/controller_server`。
- `nav2_lifecycle_manager/lifecycle_manager`。
- `map → odom` 静态 TF。
- 仿真机器人节点。
- HTTP/ROS2 桥接节点。

当前参数位于 [ros2_bridge/config/nav2_sim.yaml](/home/stone/learn/outdoorNav/ros2_bridge/config/nav2_sim.yaml)。控制器使用 `RegulatedPurePursuitController`，期望速度为 `0.45 m/s`，目标点位置容差为 `0.4 m`。

## 8. 真实室外机器人还需要补齐什么

### 8.1 建立真实可通行地图

中心线不能推导道路宽度。实机地图需要补测：

- 道路边界和最小净宽。
- 建筑、围栏、路沿、台阶和沟渠。
- 长期固定障碍物。
- 禁止进入区域。
- 机器人外形和旋转所需空间。

未知区域不能因为“看起来像道路”就标记为空闲。对于会影响安全的区域，应现场测量或保留为未知。

### 8.2 建立真实定位链路

需要让定位系统持续提供：

```text
map → odom → base_link
```

可能涉及：

- GNSS/RTK 驱动发布 `NavSatFix`。
- IMU 驱动发布姿态和角速度。
- 轮速或运动里程计发布 `odom`。
- `robot_localization` 等节点融合 GNSS、IMU 和里程计。
- GNSS 天线到 `base_link` 的外参标定。
- RTK 失锁、浮点解和改正数据中断时的退化处理。

地图坐标原点、RTK 坐标参考框架和机器人实际定位坐标必须保持一致。网页中的 WGS84 经纬度目前只是由局部坐标反算得到的参考值，不能替代已经验证的实时定位链路。

### 8.3 建立实时避障链路

真实机器人还需要传感器产生障碍物数据，并进入 local costmap，例如：

- 激光雷达。
- 深度相机。
- 三维点云或其他环境感知传感器。

还要根据机器人实际尺寸配置：

- `robot_radius` 或机器人 footprint。
- 障碍层。
- 膨胀层。
- 未知空间策略。
- 传感器更新频率。

### 8.4 接入机器狗底层控制

Nav2 的控制器输出的是速度指令。机器狗底层需要负责：

- 将速度指令转换为腿式运动或底盘运动。
- 实施速度上限和加速度限制。
- 在通信丢失时停车。
- 处理急停和人工接管。
- 返回真实运动状态和故障状态。

只有这部分接口经过现场低速测试，`FollowPath` 的完成结果才有实机意义。

## 9. 从当前仿真到实机的实施路线

建议按四个阶段推进，每个阶段单独验收。

### 阶段一：接口仿真

目标：验证 Nav2 控制器和桥接接口。

- 读取仿真 PGM/YAML。
- 检查 lifecycle 状态。
- 检查 TF。
- 发送短路径。
- 验证完成和取消。

验收标准：仿真机器人能够跟踪路径并在容差内完成。

### 阶段二：真实占据地图

目标：让地图表达实际可通行区域。

- 测量道路边界和固定障碍。
- 生成真实栅格地图。
- 设置分辨率、原点和障碍阈值。
- 配置机器人 footprint 和膨胀半径。

验收标准：地图中的空闲区域、障碍区域和机器人尺寸经过现场检查。

### 阶段三：RTK 定位融合

目标：让机器人实时知道自己在 `map` 中的位置。

- 接入 GNSS/RTK。
- 接入 IMU 和里程计。
- 建立并检查完整 TF。
- 测量定位误差和短时漂移。
- 验证 RTK 状态退化时的行为。

验收标准：机器人静止和低速运动时，地图中的位置与实地标记一致。

### 阶段四：实机闭环导航

目标：在受控环境中完成逐段导航。

- 接入真实 local costmap。
- 接入机器狗速度控制。
- 低速执行短路径。
- 测试障碍物、通信中断、急停和取消。
- 再逐步增加路线长度和环境复杂度。

验收标准：机器人可以在明确的安全边界内完成导航，并且故障时能够停止。

## 11. 导师可能追问的问题

### 为什么不能直接把经纬度传给 Nav2？

因为 Nav2 需要局部连续的米制坐标。经纬度是角度坐标，不能直接表示平面距离和机器人运动方向。

### RTK 轨迹是不是导航地图？

不是。RTK 轨迹首先是一条测量轨迹。它可以生成道路中心线，但还缺少道路宽度、障碍物、未知区域和机器人安全边界。

### 中心线地图能不能直接作为 Nav2 地图？

不能直接等同。中心线适合做道路网络和路径规划；Nav2 的静态地图通常需要占据栅格。两者可以共享同一个 `map` 坐标系，但表达内容不同。

### 为什么还需要 `odom`？

`map` 适合表达全局位置，`odom` 适合表达连续短期运动。两者结合可以让定位既有全局参考，又保持运动估计的连续性。

### 当前项目为什么可以发送 `FollowPath`，却还不能用于实机？

因为 `FollowPath` 只验证了路径跟踪接口和仿真控制闭环。真实使用还需要可靠地图、实时定位、传感器避障和机器狗底层控制。

### 为什么卫星图不能直接当 Nav2 地图？

卫星图主要是视觉参考，通常没有可靠的像素级通行语义，也不一定与 RTK 坐标正确配准。它可以作为显示图层，但不能未经处理就作为障碍地图。

### RTK 固定解是不是就一定可以导航？

固定解通常比普通差分解更可靠，但仍需要检查参考框架、天线安装、遮挡、多路径、坐标外参和实际误差。定位质量状态不能单独替代完整验收。

### 已完成

- UBX/NMEA 日志解析。
- 局部东-北米制坐标转换。
- 实测中心线路网和确认的支路连接。
- 网页 A/B 路径规划。
- 完整 `nav_msgs/Path` 导出。
- Nav2 `FollowPath` 仿真闭环。
- 地图版本、配准状态和坐标系校验。

### 尚未完成

- 真实道路边界和可通行区域测量。
- 真实障碍物占据栅格。
- 独立控制点和绝对精度验证。
- GNSS、IMU、里程计融合。
- 真实 local costmap 和动态避障。
- 机器狗底层速度控制和急停联调。

### 当前风险

- 现有数据主要为差分解，绝对精度尚未独立验证。
- 中心线不能代表道路宽度。
- 当前仿真地图是均匀自由空间。
- 当前配置关闭控制器碰撞检测。
- 当前桥接明确拒绝可直接上机器人的路线。

因此，当前最准确的项目表述是：

> 本项目完成了“实测 RTK 路线到 Nav2 控制器仿真”的验证，正在向“具备真实地图、真实定位、实时避障和真实底盘控制的室外导航系统”推进。
